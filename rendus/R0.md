## 1. CU-01 : Estimer le backlog d'un projet

| Rubrique | Contenu |
|---|---|
| **Portée et niveau** | application CAPI · utilisateur |
| **Acteur principal** | Chef de projet |
| **Intervenants et intérêts** | Chef de projet : souhaite obtenir une estimation du backlog pour planifier le projet |
| | Développeurs : souhaitent estimer les fonctionnalités sans être influencés par les votes des autres |
| | Équipe projet : souhaite disposer d'estimations cohérentes pour organiser le développement |

| **Déclencheur** | Un utilisateur souhaite organiser une session d'estimation des fonctionnalités d'un projet |
| **Garanties** | Minimales : Les votes individuels restent masqués jusqu'à la révélation et le backlog importé n'est pas modifié en cas d'échec du chargement · De succès : Les fonctionnalités du backlog ont été estimées selon les règles de validation de la session et les résultats peuvent être exportés |

### Scénario nominal (5 à 7 étapes)

1. Le participant configure la session d'estimation en choisissant les paramètres nécessaires
2. Le participant charge un fichier JSON contenant le backlog du projet
3. Le système vérifie le fichier et affiche les fonctionnalités à estimer
4. Le participant lance l'estimation d'une fonctionnalité et chaque joueur sélectionne sa carte sans voir les votes des autres
5. Le participant demande la révélation des votes et le système affiche les cartes choisies ainsi que le résultat du vote
6. Le système vérifie la validation de l'estimation selon les règles de la session. Si nécessaire, les participants procèdent à un nouveau vote jusqu'à ce que l'estimation soit validée
7. Le participant exporte les résultats des estimations du backlog
### Extensions (3 obligatoires)

- **<étape>a.** Le backlog chargé est invalide :
  - <étape>a1. Le système informe le participant que le fichier ne peut pas être chargé
  - <étape>a2. Le participant sélectionne un autre fichier et recommence le chargement
- **<étape>b.** Tous les joueurs jouent la carte café :
  - <étape>b1. Le système détecte que tous les participants ont choisi la carte café
  - <étape>b2. La session suit le comportement prévu par les règles du Planning Poker pour ce cas
- **<étape>c.** L'utilisateur reprend une partie sauvegardée :
  - <étape>c1. Le participant sélectionne une partie sauvegardée
  - <étape>c2. Le système restaure la session et affiche son état afin que le participant puisse continuer l'estimation

## 2. Les 6 user stories

| US | Texte (En tant que... je veux... afin de...) | Source | MoSCoW |
|---|---|---|---|
| US-01 |En tant que participant, je veux configurer une session et charger un backlog JSON afin de préparer les fonctionnalités à estimer |CU-01 |Must |
| US-02 |En tant que participant, je veux voter sans voir les votes des autres, révéler les résultats et recommencer un vote si nécessaire afin de réaliser une estimation collective |CU-01, CU-02 |Must |
| US-03 |En tant que participant, je veux appliquer la règle stricte de validation afin de déterminer si une estimation est acceptée |Règle stricte |Must |
| US-04 |En tant que participant, je veux choisir une règle de validation pour la session afin d'adapter les conditions d'acceptation des estimations |Règle choisie |Must |
| US-05 |En tant que participant, je veux appliquer la règle du premier tour à l'unanimité afin de traiter le premier vote conformément aux règles de la session |Premier tour à l'unanimité |Must |
| US-06 |En tant que participant, je veux sauvegarder et reprendre une partie puis exporter les résultats afin de conserver et récupérer le travail effectué |CU-01 |Must |

Parmi ces 6 US, 3 portent les règles de validation : règle stricte, règle choisie, premier tour à l'unanimité.
